## `api-key-priority-over-quota`

The request behind the account priority knobs said prioritisation "applies to oauth accounts and API key accounts". What was built for keys is ordering among keys only: a key's `weight` (and its per-model `by_model` rules) decides which eligible key is tried first, and keys are still spent only when no subscription profile can take the work. The weekly-reset override does not apply to keys at all. The other reading was not built, and it was never put to the owner. Under that reading, a key can be prioritised ahead of profiles that still have quota: for example, to burn included API credit that lapses unspent at month end. A weight or a moved month-end would then pull the key forward. Building it reverses the documented "last resort" rule for keys. It needs its own design for scoring a key (remaining budget less reserve, per hour until the month ends in `reset_tz`, times its weight) on a scale comparable with a profile's percent-of-quota-per-hour score. Done when the owner has either ruled it not wanted, or keys can be configured to compete with profiles and the README "API key accounts" section says when that spends money. Code site: the key decision in `choose` in `src/select.rs`.

## `claude-stream-liveness`

`ccc` reads a Claude turn's `stream-json` events once, after the child exits. A turn the provider has already refused can stay open for as long as a background command the agent started keeps running (on 2026-11-11 a refused designer sat for 33 minutes behind a wait loop that could not end), and a child that has gone silent looks the same as one that is working. Reading the events as they arrive would let `ccc` end a turn the moment its refusal is reported, and report a turn that has produced nothing for a set time. To settle first: what counts as stuck and for how long, whether `ccc` kills or only reports, and what happens to background commands the agent left running. Done when a refused turn ends without waiting for its background work, under a policy the owner has chosen.

## `key-spend-on-flags-without-usage-data`

The rule for when an API key is spent, as the owner wrote it in commit `76e50c5` (release 0.5.1): the best usable profile with a positive score takes the turn; else, "when usage data is unavailable entirely (broker unreachable, daemon offline) and there are candidates, configured order picks one and no key is considered"; else an API key takes it. Profile exhausted flags were built after that rule, and one case of its exception was changed with them: when usage data is unavailable and every candidate profile carries an exhausted flag in force for the model, an in-budget API key now takes the turn. With at least one unflagged candidate the owner's exception holds as written: the first unflagged profile in configured order takes the turn and no key is considered. The change was ruled by the forester agent acting for the owner at a design gate, not by the owner. The owner has not decided it. The cost as built: a key can be charged while the daemon is down on the strength of flags alone, including a flag still in force after the provider lifted the limit early. That spend is capped by the key's budget, ends at the flag's reset time, and `ccc budget clear <profile>` lifts a stale flag. The cost the other way: the turn goes to a profile recorded as refusing it, and the invocation can end in exit 4 with a key configured and in budget. To reverse it, restore the owner's exception as written: the usage-unknown branch of `choose` is taken whenever usage data is unavailable and there is a candidate, flagged or not. In the code that means replacing the "some candidate is not flagged" condition on that branch with "there is a candidate" (`!candidates.is_empty()`, as at `76e50c5`). Do not simply remove it: it is also the only thing that sends "usage data unavailable and no candidate" to the key, which the owner's rule requires, and the "only profile excluded" case of the selection test `every_profile_out_of_quota_overflows_to_the_key_with_a_note` fails if that is lost. Then rewrite the last two sentences of the "When a key is spent" paragraph of the README and the matching line of the CHANGELOG, and change the every-candidate-flagged cases of the selection test `without_usage_data_a_flagged_profile_is_skipped_and_no_key_is_considered` to expect the first candidate and no key. Done when the owner has ruled which way the exception extends to flagged profiles, and the code, README and tests agree with the ruling. Code site: the usage-unknown branch of the key decision in `choose` in `src/select.rs`.

## `subscription-usage-data-unpublished`

For a subscription account `ccc` publishes one thing into the agent tree: the exhausted flags, one per quota, in the account record (period `-`, `usd` 0, no turn count). The request behind the flags said other usage data could be reported too; none is, and the owner has not decided whether any is wanted. The usage daemon already publishes, per account and from its own poll of the usage API: the login state, the subscription type, and the utilization and reset time of every quota window (5-hour, 7-day, and each model-scoped cap), retained on the broker. So the quota levels are not missing. What only `ccc` sees, and nobody publishes: (1) the rate-limit status Claude Code reports on every turn, successful ones included — allowed, warning or rejected, with utilization and reset time per window — which is newer than the daemon's last poll at the moment a turn ends; (2) the overage state of the account (whether extra usage is enabled, in use, or refused, and why), which the daemon does not publish at all; (3) what `ccc` itself ran on the account, per host: turns, tokens per model, and the list-price cost Claude Code reports for a turn that was not billed. To settle first: whether any of these is wanted; for (1), whether selection should prefer a turn's reading over the daemon's snapshot and how the two are reconciled; for (3), whether a list-price figure in the `usd` field of a subscription record would be read as money spent, since readers sum that field. Done when the owner has ruled each of the three wanted or not, and the wanted ones are in the account record and the `claude-usage-mqtt` README. Code site: where `src/limits.rs` builds the profile's account record.

## `trust-scope-gate`

Every Claude spawn marks its working directory trusted in the account's `.claude.json`, unconditionally, and the marker outlives the run. A `--cwd` naming an untrusted checkout therefore runs that tree's hooks and MCP servers under the account's credentials and leaves the directory trusted for later interactive sessions. Narrowing this — an allowlist of roots, propagating only a directory some profile already trusts, or auto-trusting from `launch` alone — is a policy choice. Code site: `trust_cwd` in `src/exec.rs`.

## `log-missing-index-is-reported-as-an-error`

Every command that loads the audit catalog — `ccc log`, `ccc status`, `ccc kill`, and `ccc resume` or `ccc launch --resume` given a trace prefix — run before any agent has run prints `reading audit file …/audit/traces.jsonl … No such file or directory` on stderr, because the catalog loader they share reports every failure to read the index file the same way, and the index does not exist until the first run writes it. The empty-log case should be silent for every caller of the loader: a `NotFound` on `traces.jsonl` is "no runs yet", not an error, and should print nothing beyond what an empty index file prints; every other read error should keep its diagnostic. The README's quick start runs `ccc run` before `ccc log`, so the steps as written do not hit this; a newcomer who tries `ccc status` or `ccc log` first does. Code site: the `Err(e)` arm of `load_catalog` in `src/audit_view.rs`.

## `agent-tree-session-coordination`

With `[bus] enabled`, every `ccc run`, `resume` and `launch` publishes its invocation into the agent tree on the broker (`<prefix>/agents/<publisher>/<host>/session/<id>`; the schema is in the `claude-usage-mqtt` README), and `claude-usage-mqtt-core` has the types to decode every session there. Nothing in `ccc` reads those sessions: the only agent-tree topics `ccc` consumes are the account-spend records behind the API-key budget. So no session acts on what the others are doing — sessions still pile onto the same account at the same moment, and nothing notices another session working in the same directory. Coordinating sessions through the tree needs a policy first: what a session looks at (account, model, cwd, the number of live sessions), what it does about it (pick another account, wait, warn), and where that sits relative to `select::choose`. Code site: the module doc of `src/bus.rs`.

## `api-key-at-launch`

An API key account (`[claude.api_keys.*]`) cannot be used by `ccc launch`: `--profile <key>` is refused with exit 2 and selection for a launch never considers keys. An interactive Claude session reports no cost to `ccc` — a launch's end record has no `native`, and the Stop hook payload carries only the session id, the last assistant message and the transcript path — so a key used at the terminal would drain the budget without the ledger seeing it. Lifting the refusal needs a cost figure for an interactive session, per turn or at least at its end, from a source still to be found (the transcript's usage records priced per model, or a hook payload that carries cost); a launch then charges the ledger as a headless turn does. Code site: the refusal of a key account for a launch in `src/exec.rs`.

## `api-key-assumptions-unconfirmed`

API key accounts rest on three assumptions about Claude Code and the Claude Platform that have never been checked against a real key, and no test covers them. A1: `claude -p` with `ANTHROPIC_API_KEY` set bills the key, not the subscription login in `~/.claude`. A2: a turn the Platform refuses for spend reports a message that one of the key's `exhausted_patterns` matches. That is two refusals, which may not share a message: A2a, the credit is gone, which the default pattern (`*credit balance is too low*`) is a guess at; A2b, a spend limit set in the Platform console is reached, for which there is no default pattern. A3: the cost Claude Code states in `model_usage_since_last_result` on a key turn's results is within a few percent of what the Platform bills. In addition, `ccc` has never been watched publishing to a real broker: its bus is tested against a recording bus and unreachable addresses, and only the `claude-usage-mqtt` client is tested against a mosquitto. The README's "Before you rely on this" checklist, under "API key accounts", gives the command for each of the four and what it should show. Its A2 step provokes the spend-limit refusal and so settles A2b only. A2a cannot be provoked on demand: it is settled the first time the credit actually runs out, by whether that key turn exits 4 with the key shown exhausted, or exits 1 with the Platform's message in its end record. Done when the checklist has been run with a real key and broker, A2a has been settled in that way — or the user has decided that the spend limit is the only refusal they rely on — and the results are in the tree: a pattern added beside the existing ones for each refusal message that none matched (added, never put in place of one), and the README's "assumed, not tested" wording removed for whatever held. Code sites: the key branch of `Account::env_edits` in `src/harness/claude.rs` (A1); the default of `exhausted_patterns` in `src/config.rs` (A2); `charge` in `src/budget.rs` (A3).
